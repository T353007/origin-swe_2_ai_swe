# The Modern AI Stack

> **💡** *The modern AI stack is like a Swiss Army knife - except instead of a knife, corkscrew, and scissors, you have vector databases, LLM providers, and frameworks. And instead of opening wine, you're building production AI systems. Just as useful, slightly more complex.*

## Overview

The AI engineering stack consists of LLM providers, vector databases, frameworks, evaluation tools, and observability platforms. Understanding this stack helps you choose the right tools for your projects and avoid the common pitfall of "framework fatigue" - trying every new tool that comes out.

In 2024-2025, the ecosystem has matured significantly. What used to be research projects are now production-ready tools. The challenge isn't finding tools anymore - it's choosing the right ones for your specific use case without getting overwhelmed by options.

**Note:** Model versions and capabilities change rapidly. The information below reflects the state as of December 2025. Always check provider documentation for the latest model versions, pricing, and capabilities.

## Main Content

### Core Components

#### 1. LLM Providers

**OpenAI** (as of December 2025)
- **GPT-5.2** (Released December 11, 2025): Latest and most capable model, available in three variants:
  - **GPT-5.2 Pro**: Premium version for complex reasoning and quality-critical applications
  - **GPT-5.2 Thinking**: Optimized for reasoning-intensive tasks
  - **GPT-5.2 Instant**: Fast, responsive variant for real-time applications
- **GPT-4o**: Excellent multimodal model, best balance of quality and cost for most production use cases. 128K context window.
- **GPT-4o-mini**: Cost-effective alternative for simpler tasks. 128K context window.
- **text-embedding-3**: Latest embeddings in multiple dimensions (small, large, etc.)
- Best for: General-purpose tasks, production reliability, extensive tooling ecosystem
- **Check latest:** [OpenAI Models](https://platform.openai.com/docs/models) for current model availability

**Anthropic** (as of December 2025)
- **Claude 4.5 Sonnet**: Latest model, exceptional for coding tasks and complex reasoning. 200K standard context window.
- **Claude 4.5 Opus**: Premium model with extended capabilities for complex analysis tasks.
- Best for: Long context windows (up to 200K tokens standard, up to 1M extended), code generation, safety-critical applications
- **Check latest:** [Anthropic Models](https://docs.anthropic.com/claude/docs/models-overview) for current model versions

**Google** (as of December 2025)
- **Gemini 3 Pro**: Latest multimodal model with strong performance and extended context windows.
- **Gemini 3 Flash**: Fast, cost-effective version of Gemini 3 for simpler tasks.
- Best for: Integration with Google Cloud services, multimodal applications, long context needs
- **Check latest:** [Google AI Studio](https://aistudio.google.com/) for current Gemini model availability

**Open Source Options** (as of December 2025)
- **Llama 3.1** (Meta): Strong open-source option, requires self-hosting or cloud deployment. Available in multiple sizes (8B, 70B, 405B parameters).
- **Mistral** models: Efficient European models (Mistral Large, Mistral Small), good for privacy-conscious deployments
- **Best for**: Cost control at scale, data privacy, customization needs
- **Note**: Open-source models require infrastructure setup and may not match commercial model quality for all tasks

#### 2. Vector Databases

Vector databases store and search embeddings efficiently. They enable semantic search, which is the foundation of RAG (Retrieval-Augmented Generation).

**Pinecone** (Managed)
- Fully managed, serverless option
- Excellent for production deployments
- Pay-per-use pricing model
- Best for: Teams that want zero infrastructure management

**Weaviate** (Self-hosted or Managed Cloud)
- Open-source with managed cloud option
- GraphQL API, hybrid search capabilities
- Strong filtering and metadata support
- Best for: Complex query requirements, hybrid search needs

**Qdrant** (Self-hosted or Managed Cloud)
- Open-source, written in Rust (high performance)
- Managed cloud available
- Good for: High-throughput use cases, cost-conscious teams

**Chroma** (Lightweight, Python-first)
- Simplest to get started with
- Great for development and prototyping
- Can be embedded or run as a server
- Best for: Getting started quickly, small to medium datasets

**Milvus** (Self-hosted or Managed Cloud)
- Scalable, production-grade
- Supports billions of vectors
- Best for: Large-scale applications, enterprise deployments

#### 3. Frameworks & Orchestration

Frameworks abstract away the complexity of building LLM applications, providing reusable patterns and integrations.

**LangChain** (Most Popular)
- Comprehensive framework for building LLM applications
- Strong ecosystem of integrations (200+ integrations)
- Excellent for: Agents, chains, RAG applications, rapid prototyping
- Language: Python and TypeScript/JavaScript
- Best for: Most use cases, when you need flexibility and ecosystem support

**LlamaIndex** (Data-Focused)
- Specialized in data ingestion, indexing, and retrieval
- Excellent query engines and data connectors
- Best for: RAG applications, data-heavy use cases, when retrieval is your core concern
- Language: Python

**Haystack** (Open-Source NLP Framework)
- Open-source framework with strong NLP capabilities
- Good for: Document processing, question answering, semantic search
- Language: Python
- Best for: Teams wanting fully open-source solutions

**Semantic Kernel** (Microsoft Ecosystem)
- Microsoft's framework for AI applications
- Integrates with Azure services
- Best for: Teams heavily invested in Microsoft/Azure ecosystem
- Language: Python, C#, Java

**When to Choose What?**
- **LangChain**: Default choice for most applications, strongest ecosystem
- **LlamaIndex**: When data ingestion and retrieval are your primary focus
- **Haystack**: When you need open-source NLP capabilities
- **Semantic Kernel**: When building on Azure/Microsoft stack

#### 4. Evaluation & Testing

Evaluating AI systems is fundamentally different from traditional software testing. You can't use simple unit tests - you need to measure quality, relevance, accuracy, and consistency.

**LangSmith** (Commercial)
- Built by LangChain team
- Comprehensive evaluation, debugging, and monitoring
- Integrated with LangChain workflows
- Best for: Teams using LangChain, need production-grade evaluation tools

**Phoenix** (Open-Source)
- Open-source observability platform
- Excellent for tracing, debugging, and evaluation
- Developed by Arize AI
- Best for: Teams wanting open-source observability, cost-conscious deployments

**RAGAS** (Open-Source Evaluation Framework)
- Specialized for RAG evaluation
- Metrics: faithfulness, answer relevancy, context precision/recall
- Best for: RAG-specific evaluation needs

**Custom Evaluation Frameworks**
- Build your own using LLMs-as-judges
- Fine-tune evaluation metrics for your use case
- Best for: Highly specialized requirements, when off-the-shelf tools don't fit

#### 5. Observability & Monitoring

AI systems require specialized observability because traditional metrics don't capture what matters: quality, token costs, prompt performance, and model behavior.

**Tracing**
- **LangSmith**: End-to-end tracing for LangChain applications
- **OpenTelemetry**: Standard for distributed tracing (works with AI workloads)
- **Custom Tracing**: Log prompt/response pairs, token usage, latency

**Logging**
- Structured logging is essential: log prompts, responses, metadata (model, temperature, tokens)
- Store logs in searchable format (JSON)
- Include user context, session IDs, and request IDs

**Metrics to Track**
- **Latency**: Time to first token, total generation time
- **Cost**: Token usage per request, cost per user/feature
- **Quality**: Custom quality scores, user feedback, evaluation results
- **Reliability**: Error rates, rate limit hits, timeout occurrences
- **Usage**: Request volume, popular prompts, feature adoption

## Code Examples

### Basic Stack Integration Example

Here's a complete example showing how these components work together in a simple RAG (Retrieval-Augmented Generation) application:

```python
from langchain_openai import ChatOpenAI, OpenAIEmbeddings
from langchain_pinecone import PineconeVectorStore
import os

# Initialize LLM (using GPT-4o model as of December 2025)
# Note: GPT-5.2 is the latest (released Dec 11, 2025), but GPT-4o offers best value
# Always check OpenAI documentation for latest model names: GPT-5.2 Pro, GPT-5.2 Thinking, GPT-5.2 Instant
llm = ChatOpenAI(
    model="gpt-4o",  # Balanced choice: GPT-5.2 is latest but GPT-4o offers excellent quality/cost ratio
    temperature=0,   # Deterministic for consistency
)

# Initialize embeddings
embeddings = OpenAIEmbeddings(
    model="text-embedding-3-small"  # Latest embedding model
)

# Initialize Pinecone vector store (assuming index already exists)
# You'll need: pip install langchain-pinecone pinecone-client
vectorstore = PineconeVectorStore(
    index_name="my-documents-index",
    embedding=embeddings,
)

# Simple RAG chain
def answer_question(question: str) -> str:
    """
    Answer a question using RAG: retrieve relevant context, then generate answer.
    
    Args:
        question: User's question
        
    Returns:
        Generated answer based on retrieved context
    """
    # Step 1: Retrieve relevant documents (semantic search)
    docs = vectorstore.similarity_search(question, k=3)
    
    # Step 2: Build context from retrieved documents
    context = "\n\n".join([doc.page_content for doc in docs])
    
    # Step 3: Construct prompt with context
    prompt = f"""Use the following context to answer the question.
If the context doesn't contain the answer, say "I don't have enough information."

Context:
{context}

Question: {question}

Answer:"""
    
    # Step 4: Generate answer using LLM
    response = llm.invoke(prompt)
    return response.content

# Usage example
if __name__ == "__main__":
    answer = answer_question("What is the main topic of the documents?")
    print(answer)
```

**Key Points:**
- GPT-5.2 (released Dec 11, 2025) is the latest model, available as Pro, Thinking, and Instant variants
- Using `gpt-4o` in this example - it offers excellent quality/cost balance for most use cases
- Using `text-embedding-3-small` (current embedding model)
- This is a simplified example - production code would include error handling, logging, and evaluation
- Always check OpenAI's documentation for the latest model names and capabilities before deploying

## Common Mistakes

#### 1. Tool overload
Don't use every framework and tool just because they exist. Each tool adds complexity and maintenance burden. Choose based on your actual needs: if you're building a simple RAG app, you don't need LangChain agents. Start simple, add complexity only when needed.

#### 2. Vendor lock-in without abstraction
Locking yourself into a single LLM provider or vector database makes switching expensive later. Consider abstraction layers (like LangChain's LLM abstraction) so you can swap providers if pricing or features change. However, don't over-engineer - premature abstraction is also a mistake.

#### 3. Ignoring costs
Vector databases and LLM APIs can get expensive fast, especially at scale. A common mistake: using expensive models (like GPT-5.2 or GPT-4o) for simple tasks that GPT-4o-mini could handle. Monitor costs from day one, set budgets, and use cost-effective models where appropriate. GPT-5.2 is the latest and most capable, but GPT-4o-mini handles most tasks at a fraction of the cost.

#### 4. No observability
Deploying without tracing makes debugging production issues nearly impossible. When your AI system produces wrong answers, you need to see: what was the prompt? What context was retrieved? What was the model response? Without observability, you're flying blind.

#### 5. Choosing tools based on hype, not fit
New tools launch constantly. Resist the urge to rewrite everything when a new framework launches. Evaluate tools based on: does it solve your specific problem? Is it maintained? Does your team have expertise? Community size and maturity matter more than being the "latest" thing.

#### 6. Not considering data privacy and compliance
Some tools require sending data to external services. If you're handling PII or sensitive data, consider self-hosted options (like self-hosted vector DBs) or tools that process data on-premise. GDPR and other regulations apply to AI systems too.

```python
import time
import json
from datetime import datetime

def log_llm_call(prompt: str, model: str, response: str, tokens: dict = None):
    log_entry = {
        "timestamp": datetime.now().isoformat(),
        "model": model,
        "prompt": prompt,
        "response": response,
        "tokens": tokens or {},
    }
    print(json.dumps(log_entry, indent=2))
    # In production, send this to your logging service

# Use it
start_time = time.time()
response = llm.invoke("What is AI engineering?")
duration = time.time() - start_time

log_llm_call(
    prompt="What is AI engineering?",
    model="gpt-4o-mini",
    response=response.content,
    tokens={"duration_seconds": duration}
)
```
