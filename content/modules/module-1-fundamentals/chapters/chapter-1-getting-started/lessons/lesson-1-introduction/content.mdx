# Introduction to AI Engineering

> **💡** *If traditional software engineering is like playing chess, AI engineering is like playing poker—same table, completely different rules, and your unit tests just became probability distributions.*

## Overview

AI engineering is the discipline of building, deploying, and maintaining production-ready AI systems. Unlike traditional software engineering, AI engineering requires understanding probabilistic systems, managing model APIs, handling token costs, and building robust evaluation frameworks.

This field has exploded in recent years—what was cutting-edge research in 2022 is now production code in 2024. Companies that built AI features are seeing massive adoption, while those who ignored it are scrambling to catch up. The good news? You don't need a PhD to build production AI systems. You need solid engineering fundamentals, curiosity, and this course.

## Main Content

### What Makes AI Engineering Different?

Understanding the fundamental differences between traditional software engineering and AI engineering is crucial for success in this field.

**Traditional Software Engineering:**
- **Deterministic behavior**: Same input always produces same output
- **Test with unit tests**: Write tests that verify exact outputs  
- **Debug with logs**: Standard debugging with log statements and breakpoints
- **Predictable performance**: Execution time and resource usage are consistent
- **Version control for code**: Git tracks code changes
- **Deployment is straightforward**: Build, test, deploy pipeline

**AI Engineering:**
- **Probabilistic outputs**: Same input can produce different outputs (temperature, randomness)
- **Requires evaluation frameworks**: Can't use simple unit tests; need to measure quality, relevance, accuracy
- **Debug with traces and evals**: Need to trace LLM calls, analyze token usage, evaluate outputs
- **Variable performance and costs**: Latency varies, costs scale with token usage
- **Version control for prompts**: Prompts are code that need versioning and testing
- **Deployment requires monitoring**: Need to monitor quality, costs, and performance continuously

### Real-World Example: The Difference

Consider a simple function to add two numbers:

**Traditional Software:**
```python
def add(a: int, b: int) -> int:
    return a + b

# Test
assert add(2, 3) == 5  # Always true
```

**AI Engineering:**
```python
from openai import OpenAI

client = OpenAI()  # API key from OPENAI_API_KEY env var

def summarize_text(text: str) -> str:
    response = client.chat.completions.create(
        model="gpt-4o",  # Latest model (as of 2024)
        messages=[{"role": "user", "content": f"Summarize: {text}"}]
    )
    return response.choices[0].message.content

# Can't test with assert - need evaluation
# Output varies, quality is subjective, cost depends on text length
```

### Key Responsibilities of an AI Engineer

#### 1. System Design
Architect AI applications that integrate LLMs, vector databases, and other AI tools. This involves choosing the right model for each task (cost vs quality trade-offs), designing RAG pipelines, integrating multiple AI services, and creating scalable architectures.

#### 2. Prompt Engineering  
Craft effective prompts that produce reliable outputs. This includes writing clear instructions, using few-shot examples, structuring prompts for consistency, testing and iterating, and version controlling prompts as code.

#### 3. Evaluation
Build and run evaluation frameworks to ensure quality: creating test datasets, defining quality metrics (relevance, accuracy, faithfulness), running automated evaluations, and tracking results over time.

#### 4. Cost Management
Optimize token usage and API costs by monitoring consumption, choosing cost-effective models, implementing caching, setting budgets and alerts, and optimizing prompts.

#### 5. Reliability
Handle failures, rate limits, and edge cases with retry logic, graceful rate limit handling, fallback strategies, error handling, and circuit breakers.

#### 6. Deployment
Deploy AI systems to production with proper monitoring, observability (tracing, logging, metrics), quality/cost/latency monitoring, deployment strategies, and security.

### The Modern AI Stack

Understanding the tools and technologies helps you make informed decisions:

**LLM Providers**: OpenAI (GPT-4o, GPT-4-turbo, most widely used), Anthropic (Claude Sonnet, Opus), Google (Gemini), Open Source (Llama, Mistral)

**Vector Databases**: Pinecone (managed), Weaviate (open-source, GraphQL), Qdrant (self-hosted), Chroma (lightweight, Python-first)

**Frameworks**: LangChain (most popular, agents), LlamaIndex (data ingestion, RAG), Haystack (open-source NLP), Semantic Kernel (Microsoft)

**Evaluation Tools**: LangSmith (debugging, monitoring), Phoenix (open-source observability), RAGAS (RAG evaluation), Custom frameworks

**Observability**: Tracing (LangSmith, OpenTelemetry), Logging (structured logs), Monitoring (latency, cost, quality), Alerting (quality degradation, cost spikes)

## Code Examples

Here's a simple example of calling an LLM API:

```python
from openai import OpenAI
import os

# Initialize client - API key from OPENAI_API_KEY environment variable
client = OpenAI(api_key=os.getenv("OPENAI_API_KEY"))

def get_completion(prompt: str, temperature: float = 0.7) -> str:
    """
    Simple LLM API call - but see Common Mistakes for what's missing!
    (Hint: error handling, rate limits, token counting, cost tracking)
    """
    response = client.chat.completions.create(
        model="gpt-4o",  # Latest model (faster and cheaper than gpt-4)
        messages=[{"role": "user", "content": prompt}],
        temperature=temperature,
    )
    return response.choices[0].message.content

# Usage
result = get_completion("Explain what AI engineering is in one sentence.")
print(result)
# Always track usage from the response object
# response.usage.total_tokens, response.usage.prompt_tokens, response.usage.completion_tokens
```

**Note**: This is intentionally simplified. In production, you'd add retry logic, error handling, rate limit management, and cost tracking—topics we'll cover in later lessons.

### Career Path: From Software Engineer to AI Engineer

If you're coming from traditional software engineering, you're in a great position. Your existing skills transfer more than you might think.

**What Transfers**: System design, API integration, testing mindset, DevOps practices, security principles, code review, debugging intuition

**What's New**: Probabilistic systems thinking, prompt engineering patterns, evaluation frameworks, token economics, LLM-specific debugging (tracing, evals), prompt versioning

**What Changes**: 
- **Testing**: Assertions → evaluations (quality scores, relevance metrics)
- **Debugging**: Logs → traces (LLM call chains, token usage, cost attribution)
- **Optimization**: CPU/memory → tokens and latency (different bottlenecks!)
- **Monitoring**: Uptime → quality + cost + latency (more dimensions to track)

**Common Questions:**
- *"Do I need a PhD?"* No. Strong software engineering skills + this course will get you far.
- *"Is it too late to start?"* Absolutely not. The field is moving fast, but fundamentals are stable.
- *"Should I learn everything?"* Start with fundamentals (this course), then specialize based on what you build.

## Common Mistakes

These mistakes are expensive—either in dollars or engineering time. Learn them here, not in production:

#### 1. Ignoring token costs
Not tracking usage leads to unexpected bills. A single unoptimized loop can cost hundreds of dollars. One team accidentally spent $5000 in a weekend because they forgot to add a prompt length limit.

#### 2. No error handling
LLM APIs fail, rate limit, timeout. Always implement retries with exponential backoff, fallbacks, and graceful degradation.

#### 3. Hardcoding prompts
Prompts are code—they should be versioned, tested, and reviewed. A typo in a production prompt can silently break your app.

#### 4. No evaluation
Deploying without evals means you ship bugs without knowing it. Your users will notice quality degradation before you do.

#### 5. Assuming deterministic behavior
Even with `temperature=0`, there's variation. Design systems to handle it—don't assume `assert output == expected`.

#### 6. Ignoring rate limits
Hitting rate limits in production breaks user experience. Implement queuing, batching, and proper error messages.

#### 7. Not monitoring in production
You need to monitor quality metrics (relevance, accuracy), not just uptime. A service can be "up" but producing garbage.
