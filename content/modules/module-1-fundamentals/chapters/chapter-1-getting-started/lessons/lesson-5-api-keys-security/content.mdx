# API Keys and Security Best Practices

> **💡** *API keys are like the password to your bank account, except your bank account can rack up thousands of dollars in charges if someone gets your password. And unlike your bank account, once you commit a key to git, it's in history forever. Git never forgets - which is great for code, terrible for secrets.*

## Overview

API keys are sensitive credentials that grant access to paid AI services. A leaked API key can result in unauthorized access, unexpected charges (thousands of dollars in hours), and compromised data. Proper key management is critical to prevent these security incidents.

In 2024-2025, API key security is more important than ever. As AI services become more powerful and expensive, the impact of leaked keys has increased. This lesson covers everything you need to know to secure your API keys from development to production.

## Main Content

### API Key Security Principles

These principles form the foundation of secure API key management:

#### 1. Never Commit Keys to Version Control

**Why This Matters:**
- Git history is permanent (even if you delete the file later)
- Public repos expose keys to anyone
- Private repos can be accessed by team members or compromised
- Keys in git history can be extracted with simple commands

**Common Scenarios Where Keys Get Committed:**
- Adding `.env` files before adding to `.gitignore`
- Copy-pasting code with hardcoded keys
- Committing config files with example keys that look real
- Screenshots of code in documentation

**Prevention:**
- Use `.gitignore` to exclude `.env` files
- Use pre-commit hooks to scan for secrets
- Use tools like GitGuardian or TruffleHog to scan repos
- Never use real keys in examples or documentation

#### 2. Use Environment Variables

Environment variables keep secrets out of code:
- Secrets are stored outside the codebase
- Different values for different environments (dev/staging/prod)
- Easy to update without code changes
- Standard practice across the industry

#### 3. Rotate Keys Regularly

Regular rotation limits damage from compromised keys:
- Rotate immediately if a key is exposed
- Schedule regular rotations (e.g., every 90 days)
- Rotate when team members leave
- Rotate if you suspect a compromise

#### 4. Use Least-Privilege Access

Create keys with minimum required permissions:
- Some providers allow scoped keys (read-only, specific features)
- Use separate keys for different environments
- Don't use production keys for development
- Limit key permissions to what's actually needed

#### 5. Monitor Key Usage

Monitor for unusual activity:
- Track API usage patterns
- Set up alerts for unexpected spikes
- Review usage logs regularly
- Detect compromised keys early

### Environment Variables

Environment variables are the standard way to manage secrets in modern applications. They keep secrets out of your code and make it easy to use different values for different environments.

For production applications, use proper secrets management services. These provide encryption at rest, access control, audit logs, and automatic rotation.

#### Local Development

**`.env` files** (Simplest approach)
- Use `python-dotenv` to load from `.env` files
- Add `.env` to `.gitignore`
- Create `.env.example` template (commit this, not `.env`)
- Never commit actual `.env` files

**AWS Secrets Manager**
- Encrypted storage
- Automatic rotation support
- Fine-grained access control (IAM)
- Audit logging via CloudTrail
- Cost: ~$0.40 per secret per month

**AWS Systems Manager Parameter Store**
- Free tier available (Standard parameters)
- Secure String parameters for secrets
- Integration with IAM
- Works with Lambda, ECS, EC2

- Encrypted at rest
- Access control via IAM

### Key Rotation

Regular key rotation is a security best practice. It limits the damage if a key is compromised and ensures old, unused keys don't accumulate.

#### When to Rotate Keys

**Immediately:**
- Key is exposed or suspected compromise
- Key appears in git history (even if deleted)
- Key shared accidentally (email, screenshot, etc.)
- Team member with key access leaves

**Regularly:**
- Every 90 days for production keys
- Every 180 days for development keys
- After security incidents
- When updating key permissions

#### Rotation Process

**Step 1: Generate New Key**
- Go to provider dashboard (OpenAI, Anthropic, etc.)
- Generate new API key
- Save the key securely (you'll only see it once)

**Step 2: Update Environment Variables**
- Update in your secrets management system
- For production: Update via dashboard/CLI
- For development: Update `.env` file locally

**Step 3: Deploy with New Key**
- Deploy application with new key
- Verify application works with new key
- Monitor for errors

**Step 4: Revoke Old Key**
- Wait 24-48 hours after deployment
- Verify no errors or usage from old key
- Revoke old key in provider dashboard
- **Important**: Don't revoke too early - have a grace period

#### Zero-Downtime Rotation

For production systems, rotate with zero downtime:

1. Generate new key (keep old key active)
2. Deploy with both keys (try new key first, fallback to old)
3. Once new key is verified, remove old key from code
4. Revoke old key after grace period

```python
# Example: Zero-downtime key rotation
import os

# Try new key first, fallback to old during rotation
api_key = os.getenv("OPENAI_API_KEY") or os.getenv("OPENAI_API_KEY_OLD")
```

## Code Examples

### Secure Key Loading with Validation

Production-ready function for loading and validating API keys:

```python
import os
from typing import Optional
from dotenv import load_dotenv

load_dotenv()

def get_api_key(key_name: str, required: bool = True) -> Optional[str]:
    """
    Safely retrieve API key from environment variables.
    
    Args:
        key_name: Name of environment variable
        required: If True, raise error if key not found
        
    Returns:
        API key string or None if not required and not found
        
    Raises:
        ValueError: If required key is not found
    """
    key = os.getenv(key_name)
    
    if required and not key:
        raise ValueError(
            f"{key_name} is required but not set. "
            f"Please set it in your .env file or environment variables."
        )
    
    if key:
        # Basic validation - check it's not empty or placeholder
        key = key.strip()
        if key in ["", "your-api-key-here", "sk-..."]:
            raise ValueError(f"{key_name} appears to be a placeholder, not a real key")
        
        # Optionally validate format (provider-specific)
        if key_name == "OPENAI_API_KEY" and not key.startswith(("sk-", "sk-proj-")):
            raise ValueError(
                f"{key_name} doesn't match expected OpenAI key format "
                f"(should start with 'sk-' or 'sk-proj-')"
            )
    
    return key

# Usage
try:
    openai_key = get_api_key("OPENAI_API_KEY")
    anthropic_key = get_api_key("ANTHROPIC_API_KEY", required=False)
except ValueError as e:
    print(f"❌ Configuration error: {e}")
    exit(1)
```

### Environment Validation on Startup

Validate all required environment variables when the application starts:

```python
import os
import sys
from dotenv import load_dotenv

# Required environment variables
REQUIRED_ENV_VARS = [
    "OPENAI_API_KEY",
    # Add other required variables here
]

OPTIONAL_ENV_VARS = [
    "ANTHROPIC_API_KEY",
    "LANGCHAIN_API_KEY",
]

def validate_environment():
    """Validate that all required environment variables are set."""
    load_dotenv()
    
    missing = []
    invalid = []
    
    # Check required variables
    for var in REQUIRED_ENV_VARS:
        value = os.getenv(var)
        if not value or value.strip() == "":
            missing.append(var)
        elif value.strip() in ["your-api-key-here", "sk-..."]:
            invalid.append(var)
    
    # Print errors if any
    if missing:
        print("❌ Missing required environment variables:")
        for var in missing:
            print(f"  - {var}")
        print("\nPlease set these in your .env file or environment variables.")
        sys.exit(1)
    
    if invalid:
        print("⚠️  Environment variables appear to be placeholders:")
        for var in invalid:
            print(f"  - {var}")
        print("\nPlease set actual values, not placeholders.")
        sys.exit(1)
    
    # Check optional variables (just warn)
    for var in OPTIONAL_ENV_VARS:
        value = os.getenv(var)
        if not value:
            print(f"ℹ️  Optional environment variable {var} not set")

# Call on startup
if __name__ == "__main__":
    validate_environment()
    print("✅ Environment validation passed")
```

### Secure Key Masking for Logging

Never log full API keys. Mask them in logs:

```python
def mask_api_key(key: Optional[str], show_chars: int = 4) -> str:
    """
    Mask an API key for safe logging.
    
    Args:
        key: API key to mask
        show_chars: Number of characters to show at start
        
    Returns:
        Masked key string (e.g., "sk-proj-...xxxx")
    """
    if not key:
        return "None"
    
    if len(key) <= show_chars:
        return "****"
    
    return f"{key[:show_chars]}...{key[-4:]}"

# Usage in logging
import logging
api_key = os.getenv("OPENAI_API_KEY")
logging.info(f"Using API key: {mask_api_key(api_key)}")
# Output: "Using API key: sk-p...xxxx"
```

## Common Mistakes

#### 1. Committing keys to git
This is the most common and dangerous mistake. Once committed, keys are in git history forever. Even if you delete the file and commit again, the key is still accessible via `git log`. Use `.gitignore` for `.env` files, use pre-commit hooks to scan for secrets, and if you've already committed a key, rotate it immediately - don't try to remove it from history.

#### 2. Sharing keys in screenshots or demos
Screenshots of code, terminal output, or dashboards can expose keys. Keys in screenshots get indexed by search engines, shared on social media, or saved by viewers. Always blur or mask keys in screenshots, or use example/placeholder keys for demos.

#### 3. Using the same key everywhere
Using one key for development, staging, and production is dangerous. If a development key is compromised, production is also at risk. Create separate keys for each environment, use different accounts if possible, and restrict production keys to production infrastructure only.

#### 4. No spending limits set
Without spending limits, a compromised key or buggy code can rack up thousands of dollars in hours. Always set hard limits in provider dashboards, especially for development/testing accounts. Set alerts at 50%, 75%, and 90% of budget to catch issues early.

#### 5. Logging full API keys
Logging API keys (even in development) exposes them in log files, log aggregation services, and error tracking tools. Logs can be accessed by team members, stored indefinitely, or leaked. Always mask keys in logs (show only first/last few characters) or avoid logging them entirely.

#### 6. Using API keys in frontend/client-side code
API keys in frontend code (JavaScript, mobile apps) are exposed to anyone who can view the code. Attackers can extract keys from browser dev tools, mobile app decompilation, or source code inspection. Never use API keys in client-side code - use a backend API proxy instead.

#### 7. Not rotating keys after exposure
If a key is exposed (committed to git, in screenshot, etc.), you must rotate it immediately. Don't assume it hasn't been used - attackers scan public repos automatically. Generate a new key, update everywhere it's used, then revoke the old key. Waiting even a few hours can be costly.

#### 8. Storing keys in code comments or documentation
Keys in comments, README files, or documentation can be committed and shared. Example keys that look real can be accidentally used. Always use clear placeholders like `your-api-key-here` or `sk-...` in documentation, never real keys even for examples.

#### 9. Not validating keys on startup
Failing to validate that required keys are set leads to runtime errors in production. Validate all required environment variables when the application starts, provide clear error messages, and fail fast if keys are missing or invalid.

#### 10. Sharing keys via insecure channels
Sharing keys via email, Slack, or other messaging platforms exposes them to interception and accidental sharing. Use secure channels (encrypted messaging, secrets management systems) or better yet, give team members their own keys with appropriate permissions.
