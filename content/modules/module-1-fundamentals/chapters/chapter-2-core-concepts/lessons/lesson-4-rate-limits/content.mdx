# Rate Limits and Error Handling

> **💡** *Rate limits are like traffic lights for APIs—they exist to prevent chaos, but hitting one means you're stuck waiting. The difference is that with APIs, you can implement smart retry logic that doesn't just sit there honking. Exponential backoff is your friend: wait a bit, try again, wait longer, try again. It's the API equivalent of patience.*

## Overview

API providers enforce rate limits to manage load and ensure fair usage. Production applications must handle rate limits gracefully, implement proper retry logic, and distinguish between transient errors (retry) and permanent errors (fail fast). Without proper error handling, your application will fail unpredictably in production.

In 2024-2025, as AI applications scale, rate limit handling has become critical. Hitting rate limits is not a bug—it's expected behavior at scale. The key is handling them gracefully with exponential backoff, proper error classification, and monitoring.

## Main Content

### Understanding Rate Limits

Rate limits are constraints that API providers enforce to manage server load and ensure fair usage across all users. Understanding the different types helps you build systems that handle them gracefully.

#### Types of Rate Limits

**Requests per Minute (RPM)**
- Limits the number of API requests you can make per minute
- Example: 500 RPM means max 500 requests per 60-second window
- Common for: Most API endpoints
- Impact: Too many requests in a short time triggers rate limit errors

**Tokens per Minute (TPM)**
- Limits token throughput (input + output tokens combined)
- Example: 1M TPM means max 1 million tokens processed per minute
- Common for: LLM APIs (OpenAI, Anthropic)
- Impact: Large requests or high-volume usage can hit token limits even if RPM is fine

**Requests per Day (RPD)**
- Daily quota limit
- Example: 10,000 requests per day
- Common for: Free tiers, trial accounts
- Impact: Once exceeded, you're blocked until the next day

**Concurrent Requests**
- Limits simultaneous active requests
- Example: Max 10 concurrent requests
- Common for: Some providers to prevent abuse
- Impact: Too many parallel requests get queued or rejected

#### Rate Limit Headers

Most APIs return rate limit information in response headers:

```
x-ratelimit-limit: 500
x-ratelimit-remaining: 450
x-ratelimit-reset: 1234567890
retry-after: 60
```

**Important headers:**
- `x-ratelimit-remaining`: How many requests left in current window
- `retry-after`: Seconds to wait before retrying (often included in 429 responses)
- `x-ratelimit-reset`: Timestamp when the rate limit window resets

#### Common Rate Limit Scenarios

**Scenario 1: Burst Traffic**
- Your application receives a sudden spike in traffic
- RPM limit is exceeded quickly
- Solution: Implement request queuing and throttling

**Scenario 2: Large Requests**
- Individual requests consume many tokens
- TPM limit is hit even with few requests
- Solution: Reduce request size, batch smaller requests, or upgrade tier

**Scenario 3: Sustained High Volume**
- Consistent high usage over time
- Daily or hourly quotas exhausted
- Solution: Implement request prioritization, caching, or rate limiting on your side

### Error Types and When to Retry

Not all errors should be retried. Understanding error types helps you implement proper retry logic.

#### HTTP Status Codes

**429 Too Many Requests (Rate Limit)**
- **Should retry**: Yes, with exponential backoff
- **Wait time**: Check `retry-after` header or use exponential backoff
- **Action**: Wait and retry

**500, 502, 503, 504 (Server Errors)**
- **Should retry**: Yes, these are transient server issues
- **Wait time**: Exponential backoff
- **Action**: Retry with backoff

**400 Bad Request (Client Error)**
- **Should retry**: No, your request is invalid
- **Action**: Fix the request, don't retry

**401 Unauthorized (Authentication Error)**
- **Should retry**: No, authentication failed
- **Action**: Check API key, don't retry

**404 Not Found**
- **Should retry**: No, resource doesn't exist
- **Action**: Fix the endpoint/ID, don't retry

#### OpenAI-Specific Errors

**RateLimitError**
- Rate limit exceeded
- Always retry with exponential backoff

**APIError**
- Generic API error, check status_code to determine if retryable
- 5xx: Retry, 4xx: Don't retry

**APITimeoutError**
- Request timed out
- Retry with backoff

**APIConnectionError**
- Network/connection issues
- Retry with backoff

## Code Examples

### Basic Exponential Backoff Retry

Production-ready retry logic with exponential backoff:

```python
from openai import OpenAI, RateLimitError, APIError, APITimeoutError, APIConnectionError
import time
import random
from typing import Optional, Callable, Any
import os

client = OpenAI(api_key=os.getenv("OPENAI_API_KEY"))

def call_with_retry(
    prompt: str,
    max_retries: int = 3,
    initial_backoff: float = 1.0,
    max_backoff: float = 60.0,
    backoff_factor: float = 2.0,
    jitter: bool = True
) -> Optional[str]:
    """
    Call API with exponential backoff retry logic.
    
    Args:
        prompt: The prompt to send
        max_retries: Maximum number of retry attempts
        initial_backoff: Initial wait time in seconds
        max_backoff: Maximum wait time in seconds
        backoff_factor: Multiplier for each retry (2.0 = exponential)
        jitter: Add random jitter to prevent thundering herd
    
    Returns:
        Response content or None if all retries failed
    """
    for attempt in range(max_retries):
        try:
            response = client.chat.completions.create(
                model="gpt-4o",
                messages=[{"role": "user", "content": prompt}],
                max_tokens=500
            )
            return response.choices[0].message.content
            
        except RateLimitError as e:
            if attempt < max_retries - 1:
                # Calculate wait time with exponential backoff
                wait_time = min(
                    initial_backoff * (backoff_factor ** attempt),
                    max_backoff
                )
                
                # Add jitter to prevent synchronized retries
                if jitter:
                    wait_time = wait_time * (0.5 + random.random() * 0.5)
                
                print(f"Rate limited (attempt {attempt + 1}/{max_retries}). Waiting {wait_time:.2f}s...")
                time.sleep(wait_time)
            else:
                print(f"Rate limit exceeded after {max_retries} attempts")
                raise
                
        except (APITimeoutError, APIConnectionError) as e:
            # Network/timeout errors - retry
            if attempt < max_retries - 1:
                wait_time = min(
                    initial_backoff * (backoff_factor ** attempt),
                    max_backoff
                )
                print(f"Connection error (attempt {attempt + 1}/{max_retries}). Waiting {wait_time:.2f}s...")
                time.sleep(wait_time)
            else:
                raise
                
        except APIError as e:
            # Check if it's a retryable error (5xx) or client error (4xx)
            if e.status_code and e.status_code >= 500:
                # Server error - retry
                if attempt < max_retries - 1:
                    wait_time = min(
                        initial_backoff * (backoff_factor ** attempt),
                        max_backoff
                    )
                    print(f"Server error {e.status_code} (attempt {attempt + 1}/{max_retries}). Waiting {wait_time:.2f}s...")
                    time.sleep(wait_time)
                else:
                    raise
            else:
                # Client error (4xx) - don't retry
                print(f"Client error {e.status_code}: {e}")
                raise
            
    return None
```

### Advanced Retry Logic with Decorator

Reusable retry decorator for any API call:

```python
import functools
import time
import random
from typing import TypeVar, Callable
from openai import RateLimitError, APIError, APITimeoutError, APIConnectionError

T = TypeVar('T')

def retry_with_backoff(
    max_retries: int = 3,
    initial_backoff: float = 1.0,
    max_backoff: float = 60.0,
    backoff_factor: float = 2.0,
    retryable_exceptions: tuple = (RateLimitError, APITimeoutError, APIConnectionError)
):
    """
    Decorator for retrying functions with exponential backoff.
    """
    def decorator(func: Callable[..., T]) -> Callable[..., T]:
        @functools.wraps(func)
        def wrapper(*args, **kwargs) -> T:
            for attempt in range(max_retries):
                try:
                    return func(*args, **kwargs)
                    
                except retryable_exceptions as e:
                    if attempt < max_retries - 1:
                        wait_time = min(
                            initial_backoff * (backoff_factor ** attempt),
                            max_backoff
                        )
                        # Add jitter
                        wait_time = wait_time * (0.5 + random.random() * 0.5)
                        print(f"Retrying after {wait_time:.2f}s (attempt {attempt + 1}/{max_retries})")
                        time.sleep(wait_time)
                    else:
                        raise
                        
                except APIError as e:
                    # Only retry server errors (5xx)
                    if e.status_code and e.status_code >= 500:
                        if attempt < max_retries - 1:
                            wait_time = min(
                                initial_backoff * (backoff_factor ** attempt),
                                max_backoff
                            )
                            time.sleep(wait_time)
                        else:
                            raise
                    else:
                        # Client errors - don't retry
                        raise
                        
            return None
        return wrapper
    return decorator

# Usage
@retry_with_backoff(max_retries=5, initial_backoff=2.0)
def call_openai_api(prompt: str):
    response = client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": prompt}],
        max_tokens=500
    )
    return response.choices[0].message.content
```

### Using Retry-After Header

Respect the `retry-after` header when provided:

```python
def call_with_retry_after(
    prompt: str,
    max_retries: int = 5
) -> Optional[str]:
    """Call API with retry, respecting retry-after header."""
    for attempt in range(max_retries):
        try:
            response = client.chat.completions.create(
                model="gpt-4o",
                messages=[{"role": "user", "content": prompt}],
                max_tokens=500
            )
            return response.choices[0].message.content
            
        except RateLimitError as e:
            if attempt < max_retries - 1:
                # Check if retry-after header is available
                if hasattr(e, 'response') and e.response:
                    retry_after = e.response.headers.get('retry-after')
                    if retry_after:
                        wait_time = float(retry_after)
                        print(f"Rate limited. Server says wait {wait_time}s")
                    else:
                        # Fallback to exponential backoff
                        wait_time = min(2.0 ** attempt, 60.0)
                        print(f"Rate limited. Using backoff: {wait_time:.2f}s")
                else:
                    # No response object, use backoff
                    wait_time = min(2.0 ** attempt, 60.0)
                    print(f"Rate limited. Using backoff: {wait_time:.2f}s")
                
                time.sleep(wait_time)
            else:
                raise
                
    return None
```

### Comprehensive Error Handler Class

Production-ready error handling class:

```python
import logging
from typing import Optional, Dict, Any
import time
import random

logger = logging.getLogger(__name__)

class APIErrorHandler:
    """Handles API errors with retry logic and logging."""
    
    def __init__(
        self,
        max_retries: int = 3,
        initial_backoff: float = 1.0,
        max_backoff: float = 60.0,
        backoff_factor: float = 2.0,
        jitter: bool = True
    ):
        self.max_retries = max_retries
        self.initial_backoff = initial_backoff
        self.max_backoff = max_backoff
        self.backoff_factor = backoff_factor
        self.jitter = jitter
        
        self.stats = {
            "total_requests": 0,
            "successful_requests": 0,
            "retries": 0,
            "rate_limit_hits": 0,
            "failures": 0,
        }
    
    def _calculate_wait_time(self, attempt: int) -> float:
        """Calculate wait time with exponential backoff and jitter."""
        wait_time = min(
            self.initial_backoff * (self.backoff_factor ** attempt),
            self.max_backoff
        )
        
        if self.jitter:
            wait_time = wait_time * (0.5 + random.random() * 0.5)
        
        return wait_time
    
    def _is_retryable(self, error: Exception) -> bool:
        """Determine if an error should be retried."""
        if isinstance(error, RateLimitError):
            return True
        if isinstance(error, (APITimeoutError, APIConnectionError)):
            return True
        if isinstance(error, APIError):
            # Retry server errors (5xx), not client errors (4xx)
            if error.status_code and error.status_code >= 500:
                return True
        return False
    
    def execute(self, func: Callable, *args, **kwargs) -> Any:
        """Execute function with retry logic."""
        self.stats["total_requests"] += 1
        
        for attempt in range(self.max_retries):
            try:
                result = func(*args, **kwargs)
                self.stats["successful_requests"] += 1
                return result
                
            except Exception as e:
                if not self._is_retryable(e):
                    # Non-retryable error
                    self.stats["failures"] += 1
                    logger.error(f"Non-retryable error: {e}")
                    raise
                
                if attempt < self.max_retries - 1:
                    # Retryable error, wait and retry
                    self.stats["retries"] += 1
                    if isinstance(e, RateLimitError):
                        self.stats["rate_limit_hits"] += 1
                    
                    wait_time = self._calculate_wait_time(attempt)
                    logger.warning(
                        f"Retryable error on attempt {attempt + 1}/{self.max_retries}: {e}. "
                        f"Waiting {wait_time:.2f}s..."
                    )
                    time.sleep(wait_time)
                else:
                    # Max retries exceeded
                    self.stats["failures"] += 1
                    logger.error(f"Max retries exceeded: {e}")
                    raise
        
        return None
    
    def get_stats(self) -> Dict[str, int]:
        """Get error handling statistics."""
        return self.stats.copy()

# Usage
handler = APIErrorHandler(max_retries=5)

def make_api_call(prompt: str):
    return client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": prompt}],
        max_tokens=500
    )

response = handler.execute(make_api_call, "Hello!")
print(handler.get_stats())
```

## Common Mistakes

#### 1. No retry logic
Failing on the first rate limit error breaks production applications. Rate limits are expected at scale. Always implement retry logic with exponential backoff. A single rate limit error shouldn't crash your application.

#### 2. Fixed delay retries
Using a fixed delay (e.g., always wait 5 seconds) doesn't scale. If you're still rate-limited after 5 seconds, you'll hit the limit again immediately. Use exponential backoff: wait 1s, then 2s, then 4s, etc., giving the rate limit window time to reset.

#### 3. Infinite retries
Retrying forever can hang your application indefinitely. Always set a maximum number of retries (typically 3-5). After max retries, fail gracefully, log the error, and potentially queue the request for later processing.

#### 4. Retrying non-retryable errors
Client errors (4xx) like 400 Bad Request or 401 Unauthorized should never be retried. They indicate your request is invalid or authentication failed. Retrying wastes time and API calls. Only retry server errors (5xx) and rate limits (429).

#### 5. No logging or monitoring
Without logging, you can't debug rate limit issues or understand failure patterns. Log retry attempts, wait times, error types, and success rates. Monitor rate limit hits to identify when you need to upgrade your tier or optimize usage.

#### 6. No jitter in backoff
Without jitter, all retrying clients wait the same time and retry simultaneously (thundering herd problem). This can cause cascading rate limit errors. Add random jitter to backoff times to spread out retries.

#### 7. Ignoring retry-after headers
Some APIs provide `retry-after` headers telling you exactly when to retry. Ignoring this and using fixed backoff means you might wait too long (slow) or not long enough (still rate-limited). Check for and respect `retry-after` headers when available.

#### 8. Blocking retries in async code
Using `time.sleep()` in async code blocks the event loop, preventing other requests from processing. Use `asyncio.sleep()` in async contexts. For high-volume applications, consider using async retry libraries.

#### 9. Not implementing request queuing
At high volume, retries alone aren't enough. You need request queuing to throttle requests and prevent hitting rate limits in the first place. Implement a queue with rate limiting on your side to stay under API limits.

#### 10. Same retry logic for all endpoints
Different endpoints may have different rate limits. A chat completion endpoint might have 500 RPM, while embeddings might have 1000 RPM. Use different retry strategies per endpoint, and track rate limits separately.
