# Prompt Engineering Fundamentals

> **💡** *Prompt engineering is like giving directions to someone who's incredibly smart but takes everything literally - be clear, be specific, and for the love of all that's good, include examples. A bad prompt is like asking "fix my code" when you meant "review this Python function for security vulnerabilities and return a JSON list of issues." The model will try its best, but you'll get what you asked for, not what you wanted.*

## Overview

Prompt engineering is the practice of designing inputs (prompts) to get desired outputs from LLMs. It's both an art and a science - good prompts are clear, specific, structured, and include examples when needed. The difference between a good prompt and a bad prompt can be the difference between getting exactly what you need and getting something completely unusable.

In 2024-2025, prompt engineering has become a critical skill for AI engineers. Modern models like GPT-4o are incredibly capable, but they require well-crafted prompts to perform consistently. A poorly written prompt can waste API calls, produce low-quality outputs, and lead to production issues. This lesson covers the fundamentals you need to write production-ready prompts.

## Main Content

### Prompt Structure

A well-structured prompt follows a consistent pattern that guides the model to produce the desired output. While not every prompt needs all components, understanding the structure helps you build effective prompts.

#### 1. Role/Context (System Message)

Set the AI's role and context to guide its behavior:

```
You are an expert Python developer specializing in security code reviews.
```

**Why it matters:**
- Sets expectations for tone and expertise level
- Helps the model focus on relevant knowledge
- Useful for maintaining consistency across multiple interactions

**Best practices:**
- Be specific about expertise level ("expert", "senior", "beginner-friendly")
- Include domain specialization when relevant
- Keep it concise (1-2 sentences)

#### 2. Task Description

Clearly describe what you want the model to do:

```
Review this Python function for security vulnerabilities, focusing on:
- SQL injection risks
- Input validation issues
- Authentication/authorization flaws
```

**Why it matters:**
- Vague tasks lead to vague outputs
- Specific tasks get specific, actionable results
- Helps the model prioritize what to focus on

**Best practices:**
- Use action verbs ("review", "extract", "classify", "generate")
- Break complex tasks into sub-tasks
- Specify what aspects to focus on

#### 3. Input Data/Context

Provide the data the model should process:

```
Function to review:
```python
def login(username, password):
    query = f"SELECT * FROM users WHERE username='{username}' AND password='{password}'"
    return db.execute(query)
```
```

**Why it matters:**
- The model needs the actual data to process
- Format the input clearly for easy parsing
- Use code blocks for code, structured formats for data

**Best practices:**
- Use markdown code blocks for code
- Clearly separate different inputs
- Include relevant metadata when helpful

#### 4. Output Format

Specify exactly how you want the output structured:

````
Return your findings as a JSON array with this structure:

```json
{
  "vulnerabilities": [
    {
      "type": "SQL injection",
      "severity": "critical",
      "line": 2,
      "description": "...",
      "fix": "..."
    }
  ]
}
```
````

**Why it matters:**
- Consistent formats are easier to parse programmatically
- Reduces need for post-processing
- Prevents format inconsistencies

**Best practices:**
- Use structured formats (JSON, XML, YAML) for programmatic use
- Show the exact structure you expect
- Include examples of valid outputs

#### 5. Examples (Few-Shot Learning)

Provide examples of good inputs and outputs:

````
Example:
Input: "def get_user(id): return db.execute(f'SELECT * FROM users WHERE id=' + id)"
Output: 

```json
{"vulnerabilities": [{"type": "SQL injection", "severity": "critical", ...}]}
```

Now review the function above.
````

**Why it matters:**
- Examples teach the model the desired format and style
- Especially helpful for nuanced tasks
- Reduces ambiguity

**Best practices:**
- Use 2-4 examples for few-shot learning
- Make examples representative of the task
- Include edge cases when relevant

#### 6. Constraints and Rules

Specify limitations, rules, or requirements:

```
Constraints:
- Only report critical and high severity issues
- Provide specific line numbers
- Suggest concrete fixes
- Maximum 10 issues per review
```

**Why it matters:**
- Prevents unwanted outputs (too long, wrong focus, etc.)
- Sets boundaries for the model
- Ensures outputs meet your requirements

**Best practices:**
- List constraints explicitly
- Use bullet points for clarity
- Include limits (max length, max items, etc.)

### Basic Prompt Patterns

#### Simple Instruction

For straightforward tasks, a direct instruction works:

```
Translate the following text to French: "Hello, how are you?"
```

**Use when:**
- Task is simple and unambiguous
- No special formatting needed
- Single, clear output expected

#### Instruction with Role/Context

Add context to guide behavior:

```
You are a helpful coding assistant. Explain what this Python code does in simple terms:

```python
def fibonacci(n):
    if n <= 1:
        return n
    return fibonacci(n-1) + fibonacci(n-2)
```
```

**Use when:**
- Need specific tone or expertise level
- Context helps the model understand expectations
- Task benefits from specialized knowledge

#### Few-Shot Learning

Provide examples to teach the desired pattern:

```
Classify the sentiment of these product reviews:

Review: "Great product, highly recommended!" → Sentiment: Positive
Review: "Not worth the money, very disappointed" → Sentiment: Negative
Review: "It's okay, nothing special" → Sentiment: Neutral
Review: "Amazing service and fast shipping!" → Sentiment: Positive
Review: "Terrible quality, broke after one week" → Sentiment: ?
```

**Use when:**
- Task has nuanced categories or formatting
- Examples clarify edge cases
- Consistent format is critical

#### Structured Output Pattern

Specify exact output format for programmatic use:

````
Extract the following information from this text and return as JSON:

Text: "John Smith, age 35, lives in San Francisco and works as a software engineer."

Format:

```json
{
  "name": "string",
  "age": number,
  "location": "string",
  "occupation": "string"
}
```
````

**Use when:**
- Output needs to be parsed programmatically
- Consistent structure is required
- Integration with code is needed

### Advanced Techniques

#### Chain-of-Thought (CoT) Prompting

Encourage the model to show its reasoning process:

```
Solve this math problem step by step, showing your reasoning:

Problem: If a train travels 60 mph for 2 hours, how far does it go?

Think through this step by step:
1. First, identify what you know
2. Then, determine what you need to find
3. Finally, apply the appropriate formula
```

**Why it works:**
- Models perform better on complex reasoning when they "think aloud"
- Helps catch errors in the reasoning process
- Makes outputs more interpretable

**Use when:**
- Complex problem-solving tasks
- Math or logic problems
- Multi-step reasoning required

#### Zero-Shot vs Few-Shot

**Zero-Shot**: No examples, just instructions
```
Classify this email as spam or not spam: "[email content]"
```

**Few-Shot**: Include examples
```
Classify emails as spam or not spam:
Email: "You've won $1,000,000!" → Spam
Email: "Meeting tomorrow at 3pm" → Not Spam
Email: "Free money, click here!" → ?
```

**When to use each:**
- **Zero-shot**: Simple, well-defined tasks
- **Few-shot**: Nuanced tasks, specific formatting needed, edge cases matter

#### Role-Playing

Set a specific role to get specialized behavior:

```
You are a senior software architect reviewing a system design. Evaluate this architecture:

[architecture description]

Focus on:
- Scalability concerns
- Potential bottlenecks
- Missing components
- Alternative approaches
```

**Use when:**
- Need expert-level analysis
- Want specific perspective or expertise
- Need consistent tone/style

#### Iterative Refinement

Break complex tasks into steps:

```
Step 1: Read this code and identify the main function
Step 2: List all external dependencies
Step 3: Identify potential security issues
Step 4: Suggest improvements

Code:
[code here]
```

**Use when:**
- Task is multi-faceted
- Need structured output with multiple components
- Want to ensure all aspects are covered

#### Constraint-Based Prompting

Set explicit constraints to control output:

```
Write a product description (max 100 words) that:
- Highlights the key features
- Uses professional but friendly tone
- Includes a call-to-action
- Avoids marketing jargon

Product: [product details]
```

**Use when:**
- Need to enforce specific requirements
- Output must meet certain criteria
- Want to prevent common issues (too long, wrong tone, etc.)

## Code Examples

### Systematic Prompt Building

Production-ready prompt builder with proper structure:

```python
from typing import List, Optional, Dict, Any

def build_prompt(
    role: str,
    task: str,
    input_data: str = "",
    context: str = "",
    examples: Optional[List[str]] = None,
    output_format: str = "",
    constraints: Optional[List[str]] = None
) -> str:
    """
    Build a structured prompt with all components.
    
    Args:
        role: The AI's role/identity
        task: Description of what to do
        input_data: The data to process
        context: Additional context
        examples: Few-shot examples
        output_format: Desired output format
        constraints: List of constraints/rules
        
    Returns:
        Complete prompt string
    """
    prompt_parts = []
    
    # 1. Role/Context
    prompt_parts.append(f"You are {role}.\n")
    
    # 2. Context (if provided)
    if context:
        prompt_parts.append(f"Context: {context}\n")
    
    prompt_parts.append("")  # Blank line
    
    # 3. Task description
    prompt_parts.append(f"Task: {task}\n")
    
    # 4. Input data
    if input_data:
        prompt_parts.append(f"\nInput:\n{input_data}\n")
    
    # 5. Examples (few-shot)
    if examples:
        prompt_parts.append("\nExamples:")
        for i, ex in enumerate(examples, 1):
            prompt_parts.append(f"\nExample {i}:\n{ex}")
        prompt_parts.append("")
    
    # 6. Output format
    if output_format:
        prompt_parts.append(f"\nOutput format: {output_format}\n")
    
    # 7. Constraints
    if constraints:
        prompt_parts.append("\nConstraints:")
        for constraint in constraints:
            prompt_parts.append(f"- {constraint}")
        prompt_parts.append("")
    
    return "\n".join(prompt_parts)

# Usage example
prompt = build_prompt(
    role="an expert Python security reviewer",
    task="Review this Python function for security vulnerabilities",
    input_data='''```python
def login(username, password):
    query = f"SELECT * FROM users WHERE username='{username}' AND password='{password}'"
    return db.execute(query)
```''',
    context="Focus on SQL injection, input validation, and authentication issues",
    output_format='''JSON array with structure:
{"vulnerabilities": [{"type": "string", "severity": "critical|high|medium|low", "line": number, "description": "string", "fix": "string"}]}''',
    constraints=[
        "Only report critical and high severity issues",
        "Provide specific line numbers",
        "Maximum 10 issues per review"
    ]
)

print(prompt)
```

### Prompt Template System

Create reusable prompt templates for common patterns:

```python
class PromptTemplate:
    """Reusable prompt template system."""
    
    def __init__(self, template: str):
        self.template = template
    
    def format(self, **kwargs) -> str:
        """Format template with provided variables."""
        return self.template.format(**kwargs)

# Define templates
CODE_REVIEW_TEMPLATE = PromptTemplate("""You are an expert {language} developer.

Review this code for {focus_areas}:

```{language}
{code}
```

Return findings as JSON:
{output_format}

Constraints:
{constraints}
""")

# Usage
prompt = CODE_REVIEW_TEMPLATE.format(
    language="Python",
    focus_areas="security vulnerabilities",
    code="def login(u, p): return db.execute(f'SELECT * FROM users WHERE u={u}')",
    output_format='{"issues": [{"type": "...", "severity": "..."}]}',
    constraints="- Only critical/high severity\n- Max 10 issues"
)
```

### Prompt Versioning

Version your prompts for tracking and iteration:

```python
class PromptVersion:
    """Track prompt versions and variations."""
    
    def __init__(self, version: str, prompt: str, description: str = ""):
        self.version = version
        self.prompt = prompt
        self.description = description
    
    def __str__(self):
        return f"v{self.version}: {self.description}"

# Store different versions
PROMPT_VERSIONS = {
    "code_review_v1": PromptVersion(
        version="1.0",
        prompt=build_prompt(...),
        description="Initial version with basic structure"
    ),
    "code_review_v2": PromptVersion(
        version="2.0",
        prompt=build_prompt(...),  # Improved version
        description="Added few-shot examples, improved format"
    ),
}

# Use specific version
current_prompt = PROMPT_VERSIONS["code_review_v2"].prompt
```

## Common Mistakes

#### 1. Vague or ambiguous instructions
"Fix this code" leaves too much open to interpretation. The model doesn't know what to fix, how to fix it, or what format you want. Be specific: "Review this Python function for security vulnerabilities, identify the issues, and suggest fixes in JSON format."

#### 2. Too much or irrelevant context
Including unnecessary information dilutes the prompt's effectiveness. The model has limited attention - if you include 10 pages of context for a simple task, the important instructions get lost. Include only relevant context.

#### 3. Inconsistent output formatting
Varying formats make parsing outputs difficult. If sometimes you get JSON, sometimes plain text, sometimes markdown, your code has to handle all cases (or breaks). Always specify exact output format and stick to it.

#### 4. No examples for complex or nuanced tasks
Complex tasks with subtle distinctions need examples. If you're classifying sentiment, providing examples teaches the model your specific definitions of "positive" vs "neutral". Without examples, you get the model's default understanding, which may not match yours.

#### 5. Ignoring token limits and costs
Very long prompts cost more and may exceed model limits (8K, 128K, etc.). A 10,000-token prompt costs $0.025 per request (GPT-4o input pricing). At scale, this adds up. Be concise - include what's needed, remove what's not.

#### 6. Mixing instructions and data
Confusing structure makes prompts hard to parse (for both humans and models). Use clear sections, markdown formatting, and separators. Separate the "what to do" from the "data to process".

#### 7. Not testing prompt variations
A prompt that works for one input might fail for edge cases. Test with diverse inputs, edge cases, and different scenarios. Iterate on prompts based on real outputs, not assumptions.

#### 8. Forgetting to specify constraints
Without constraints, outputs can be too long, include unwanted content, or violate requirements. Always specify: max length, what to exclude, required elements, format requirements.

#### 9. Using the same prompt for different models
Different models (GPT-4o vs Claude vs GPT-3.5) may respond differently to the same prompt. What works for one model might not work for another. Test and adapt prompts for your specific model.

#### 10. Not versioning prompts
Prompts evolve over time. Without versioning, you can't track what changed, roll back to working versions, or A/B test improvements. Treat prompts like code - version them, test changes, and track performance.
